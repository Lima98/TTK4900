As discussed in the previous section there are several issues with the first iteration the second iteration aims to solve. Most of the improvements over the first iteration are not seen directly by the end-user as the bulk of the improvement is in how the code handles the musical objects.

The second iteration continues with the use of \textit{python} and generating \textit{lilypond} code to generate the music. This proved to be a suitable way to display not only the music as images with musical notation, but getting audio output also proved to be quite straightforward.

\section{Software architecture}
Figure~\ref{fig:iter2_architecture} shows the second iteration in the same architectural style as the other iterations. Compared with the first iteration, the generation now passes through explicit musical objects such as \texttt{Motif}, \texttt{Bar}, and \texttt{Phrase}, and the generator reuses motivic material instead of producing every event independently.

The architecture is still quite script-driven, but it is more clearly divided than in the first iteration. The main script requests a phrase, the generator module creates the musical content, the \texttt{music.py} file defines the musical objects, and the LilyPond module handles export and playback. This means that the second iteration is not yet modular in the same way as the third iteration, but it is no longer one large proof-of-concept script where everything happens at once.

The most important architectural change is really that the melody is no longer thought of only as one long sequence of notes. Instead, the generator first creates a motif, then uses that motif when building bars, and then groups the bars into a phrase. That is a simple change, but it is musically meaningful, because it is the first time the code begins to distinguish between a small musical idea, one bar of music, and a larger melodic unit.

The second iteration improved upon the structure of the melody. By using a motif we forced some self-similarity in the generated melody which helped generate something more musical, however this generation is very dependent on the generated motif itself being musical.

The generation process is also more structured than in the first iteration. The code first generates a small motif, then uses that motif at the beginning of each bar, and then fills the remainder of the bar with notes moving by 2nds or 3rds. In the final bar the generator forces a tonic ending, which is a simple way of making the melody feel at least somewhat resolved. This is still a lightweight strategy, but it is more directed than the first iteration where every note was generated with very little relation to a larger idea.

Structurally the second iteration is quite similar to the first iteration however, the objects used for handling the melodies and such are more robust and easier to understand. The most important improvement is therefore not a large increase in theoretical correctness, but that the representation now makes it possible to talk about repeated material and phrase structure in the code itself.

At the same time, the objects are still quite lightweight. A \texttt{Note} stores a MIDI number and a duration, but there is still no explicit harmonic plan, no voice profile, and no event metadata for things such as rests or chromatic adjustments. The motif handling is also mostly literal repetition rather than actual variation or development. This means that the representation is better than in the first iteration, but still too limited to support the kinds of transformations and constraints that are needed in the final system.

\section{Results}
Compared with the first iteration, the clearest improvement in the second iteration is that the melody now has some internal identity. Instead of generating one long stream of unrelated notes, the generator begins with a motif and places that motif at the start of each bar. This gives the phrase a repeated idea the listener can recognize, even when the remaining notes are still produced quite locally.

If the generated motif is not especially good, repetition does not solve the problem, it spreads it through the whole phrase. This is one of the clearest remaining weaknesses of the second iteration: it has discovered repetition, but it still lacks the melodic rules needed to make that repetition consistently convincing.

\section{Discussion}
  The most glaring issue with this iteration is that the melodic rules have not been formalized and implemented as code. Generating a melody using this restricted form of generation works well when the generated motif is good, and with the current implementation this only happens randomly. By implementing melodic rules and restrictions this generator will greatly improve the melody generation.

  In the first iteration also had the ability to generate several voices at the same time, however, this will not be re-implemented until the melodic generation has been improved and we can enforce harmonic restrictions on one voice. If this is achieved then multi-voice generation will become much more interesting. 

  Additionally the second iteration does not properly spell all notes in the different keys, this does not affect the generation in any way, though it is a trivial fix it was not implemented since the structure of the second iteration was incompatible with it. Therefore it will only be implemented in the final iteration.

  We would also like to implement augmentation of a given melody or phrase, meaning the ability to transpose it up or down or use the same rhythmic outline and moving the notes around to follow a new chord. This will help develop the generated motif and melody to follow a more structured outline of a well composed melody. A key to a good melody is self-similarity, the second iteration just has repetition of a motif, not variations of it. \\

  \section{Specifications for next iteration}
  The second iteration improves the object model, but the next step is to make those objects useful for more deliberate musical control. The third iteration should therefore build on the stronger representation from this iteration and use it to support augmentation, constraints, harmonic planning, and more flexible output.

  \begin{itemize}
    \item Implement explicit melodic constraints so that the quality of the output is not so dependent on the initial motif happening to be good.
    \item Support augmentation and transformation of already generated material, such as transposition, reuse over new harmony, and more varied motif handling.
    \item Improve the musical object model further so that it can carry more information about harmony, phrase context, and later multi-voice use.
    \item Fix practical issues such as note spelling in different keys and make the representation compatible with a more robust final implementation.
    \item Reintroduce multi-voice output in a more meaningful way, this time with harmonic awareness rather than fully independent voices.
  \end{itemize}
